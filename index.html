AI engineering / ideas & decisions

How I think about building useful agents.

The interesting work starts when a model has to operate inside a real product: incomplete information, changing state, external systems, and users who need a dependable outcome. These notes explain the design questions I care about, with examples and connections to my project work.

01 / AI agents 02 / Voice AI 03 / Applied AI

01 / Agent architecture

Give the model a useful job—and a clear boundary.

An agent needs more than instructions. It needs a representation of the task, access to relevant evidence, well-defined actions, and a way to decide whether it has finished. I’m interested in the boundary between flexible language understanding and explicit control over state and actions.

Workflows, agents, and bounded autonomy

A workflow fixes the sequence in code; an agent can choose its next step from the current context. Many useful systems combine both: let a model interpret an ambiguous answer, then let explicit rules decide whether a required fact is missing or an action is permitted.

The design question: which decisions benefit from model judgment, and which need a stable contract? For a verification flow, wording can be flexible while field ownership, completion requirements, and stop conditions remain explicit.

Reference: Anthropic on workflows and agents ↗
Context engineering, retrieval, and memory

Context engineering is the work of choosing what the model should see at a particular step: instructions, recent dialogue, retrieved material, tool results, and current state. A longer history is not automatically a better one; stale or conflicting facts can change the next decision.

Retrieval-augmented generation (RAG) supplies relevant source material. Conversation memory carries facts across turns or attempts. Neither establishes that a fact is current or applicable. A useful design records where a value came from, when it was confirmed, and what can supersede it.

Example: a plan name from yesterday’s call should not silently satisfy today’s identity check. That is a freshness and attribution problem even when retrieval returns the right document.

Reference: context engineering ↗
Tool calling, MCP, and reliable actions

A tool call turns a model decision into an operation on another system. Its contract should explain the inputs, result, errors, and side effects. The Model Context Protocol (MCP) standardizes discovery and exchange of tools, resources, and prompts; the application still owns its business rules and execution policy.

The design question: what happens if a request times out after the operation succeeded? Retrying a read and retrying a booking are different. A booking tool needs a way to identify the same intended operation and reconcile its status before creating another booking.

Permissions, argument validation, timeouts, and required approvals belong at the execution boundary. A fluent model response is not evidence that the external action completed.

Reference: MCP architecture ↗
When a multi-agent design is worth it

Separate agents can help when subtasks have distinct context or can be investigated independently. They also introduce coordination, additional model calls, and a need to reconcile conflicting results.

I would first make the single-agent baseline measurable. Then I would ask what the proposed split improves: task quality, isolation, or elapsed time. Each worker needs a bounded assignment and an explicit output contract; the final synthesis still needs verification.

Useful test: does the added agent find evidence or complete work the simpler system consistently misses, after accounting for latency and cost?

Trust boundaries, prompt injection, and human review

A document or tool result can contain instructions, but it should not gain the authority of the user or the application. Prompt-injection resistance includes keeping untrusted content separate from control instructions and limiting what tools may do.

Human review should be attached to a specific proposed action, with the evidence and consequences visible. Escalating a conversation to a person is different from requiring approval before an external write. Privacy also needs attention across transcripts, logs, traces, and test fixtures.

Reference: safety in agent design ↗

02 / Voice AI systems

The conversation has a clock.

In voice, correctness includes when the agent speaks, what it heard, and whether it can recover from an interruption. A delayed answer, a premature response, or a stale state update can change the entire call—even when the generated sentence looks reasonable in a transcript.

Speech pipelines and speech-to-speech models

A cascaded pipeline connects speech-to-text (STT), a language model, and text-to-speech (TTS). Those boundaries make it possible to inspect the transcript, control the generated text, and choose components independently. A realtime speech-to-speech model handles audio more directly and can use information beyond a text transcript.

The architecture choice depends on the product: inspectability, voice behavior, tool integration, operational control, and measured response time. Either design still needs state management, tool validation, and a clear definition of successful completion.

Reference: voice pipeline types ↗
Turn detection, endpointing, and interruptions

Voice activity detection (VAD) helps identify speech and silence. Deciding that a person has finished a thought is a separate problem: a pause may mean they are looking up a date or spelling an identifier. Endpointing and semantic turn detection influence when the agent responds.

Barge-in means the person starts speaking during the agent’s response. Good interruption handling must consider queued audio and conversation history: words generated but never heard should not be treated as delivered. Backchannels such as “mm-hmm” also need different handling from a correction.

Trade-off: respond quickly enough to feel engaged without repeatedly cutting off the caller.

Reference: turn detection and interruptions ↗
Latency budgets and the time the caller experiences

Model time-to-first-token is only one part of a voice response. The caller experiences the interval from finishing their turn to hearing useful audio. Transcription delay, end-of-turn detection, model generation, tool calls, synthesis, and playback can all contribute.

I would measure median and tail latency, then inspect stage-level traces to find the bottleneck. Streaming can overlap stages, so adding every component’s full duration can misrepresent the critical path.

A useful optimization question: did the caller get a correct, relevant response sooner, or did the system merely start an acknowledgement sooner?

Reference: voice latency stages and traces ↗
Foreground conversation and background extraction

The conversational model and the extractor do different jobs. One chooses what to say next; the other turns the conversation into structured state. If extraction runs asynchronously, the next prompt can render before the latest answer has landed.

Synthetic example: a representative says, “No exception request was filed.” The transcript contains that answer, but the state still says Unknown. A test that immediately seeds the final field skips the timing condition that could trigger an unnecessary appeal question.

I test the intermediate state as well as the final record. Question gates, completion rules, and retry summaries need to agree about what is known at that point.

IVRs, holds, transfers, and resumed calls

A phone call can move between an automated menu, hold music, a representative, and another department. These are different operating states. Menu prompts should not automatically become human-confirmed benefit facts, and a transfer may require fresh identification.

A recovery design needs to say what survives a disconnect, what must be reconfirmed, and which unanswered questions remain. A human handoff should preserve the reason for escalation and useful context without claiming an uncompleted action succeeded.

Test beyond the happy path: silence, repeated prompts, background speech, spelling corrections, partial answers, and a transfer after useful information has already been collected.

Connection to my work: recovery routes in healthcare voice workflows and tests that reproduce extraction lag.

03 / Applied AI engineering

Make quality an observable product property.

Applied AI engineering connects model behavior to the result a user or downstream system needs. That includes defining success, inspecting failures, choosing appropriate models, and making changes that remain understandable after deployment.

Structured outputs, grounding, and semantic validation

A schema can constrain field names, types, and allowed values. It cannot by itself establish that the answer is supported by the source. A valid date can belong to the wrong plan; a valid status can describe a different request.

I think about three checks: representation—is the output well formed; support—what evidence backs the value; and consistency—do related fields agree? Derived values need the same scrutiny because ordinary application code can also introduce an unsupported conclusion.

Synthetic example: copying a prior-authorization reference into an exception record can pass type validation while inventing a second request.

Reference: structured model outputs ↗
Evaluation design, regression suites, and ablation

Start with a specific behavior to measure and a dataset that includes normal cases, edge cases, and known failures. Keep holdout cases separate from examples used while tuning. For stochastic responses, repeated runs reveal variation that a single pass can hide.

Different layers answer different questions: deterministic tests check rules; prompt tests check model behavior; extraction tests check field attribution; full-flow tests check orchestration. Human review helps calibrate automated or model-based grading.

Ablation removes one part of a proposed fix to see whether the result depends on it. I also look for false passes: an empty answer or a test that never reaches the failing branch should not establish success.

Reference: evaluation design and continuous testing ↗
Model selection, routing, and cost per useful outcome

A model choice is a task-specific trade-off among quality, response time, context requirements, tool behavior, and operating cost. Conversation, extraction, and classification may have different needs, even inside one product.

I would compare candidates on the same representative scenarios and include timeouts, retries, fallbacks, and downstream corrections in the measurement. A cheaper request can become an expensive workflow if it causes repeated calls or more manual review.

Routing and fallback policies also need tests. Switching providers should preserve the output contract and error semantics, rather than silently turning a partial result into a successful one.

Observability, controlled rollout, and feedback loops

A useful trace connects the input state, prompt or model version, tool activity, extracted fields, and final decision. Metrics show where a failure is growing; the trace helps explain the individual event. Sensitive values need deliberate handling in both.

For a rollout, define who receives the change, how to identify that version later, and which conditions justify expanding or rolling back. Track outcome quality alongside latency and operational errors.

I distinguish offline replay, deployed configuration, and observed live behavior. Each is evidence about a different part of the release, and newly observed failures should become candidates for the regression set.

From a customer workflow to a product that earns trust

Before choosing an agent architecture, map the user’s actual process: the inputs they have, the decisions they make, the systems they touch, and the exceptions that send work back to a person. The most valuable automation may be a narrow, well-integrated step.

Questions I would bring to discovery: What does a correct completed task look like? Which mistakes are recoverable? Who reviews uncertainty? What happens when an integration is unavailable? How will the team distinguish saved time from work shifted into cleanup?

For a forward-deployed or product engineering role, that translation—from operating constraints to interfaces, acceptance criteria, and a feedback loop—is as important as the model call.

Connection to my work: semantic extraction fixes, evidence-preserving validation, and compatible rollout policies.
