Context Engineering at 100ms

Focus Python · TypeScript · Contract testing

Scope Selected contributions; conceptual descriptions.

The problem

A call can be evaluated during a live conversation and later recomputed from its stored output. Those paths need consistent interpretations of required fields, plan types, and completion criteria.

My contribution

I extend a shared decision engine with Python and TypeScript implementations, update common scenario datasets, and integrate releases into downstream applications. My work includes plan-dependent requirements and derived benefits logic.

The engineering contract

  1. A written manifest describes the intended business behavior.
  2. Python and TypeScript implementations follow the same contract.
  3. A common scenario corpus records expected outcomes.
  4. Both runtimes are checked against those scenarios.
  5. Consumers adopt the versioned engine.

Key tradeoffs

Share the meaning across languages. Applications can retain their existing runtimes while using equivalent decision rules. That makes cross-language tests a first-class part of the work.

Make conditional requirements visible. Fields may be required for one plan or workflow and irrelevant for another. A written contract helps reviewers reason about the intended behavior before inspecting implementation details.

Validation

I add scenarios for the changed rules and update both implementations. Regression cases exercise conditional requirements and derived values, including interactions between coverage, plan type, and coordination of benefits.

What this work enables

Changes can be reviewed as a business contract, checked across runtimes, and consumed through versioned packages. The shared corpus provides an explicit record of expected decisions.

A decision should stay consistent as it moves between applications.

This overview uses no patient data or production transcripts.

What is actually shared

The implementations are separate Python and TypeScript packages. They consume a common JSON scenario corpus describing inputs and expected decisions. Python tests and the JavaScript test suite exercise the same cases, so a rule change can be checked across both languages.

The engine supports evaluation from live context and from stored structured output. That boundary matters: nested output shapes must be interpreted consistently with the values used during a call.

Changing a rule

My workflow is to update the written behavior contract, implement the rule in both runtimes, and add cases that expose the changed condition. Examples include requirements that depend on the plan type and derived values that must not override representative-confirmed information.

This is where scenario tests, typed data, and package versioning become part of product correctness. Downstream applications can adopt the updated package while keeping the rule changes reviewable.
