The problem

A patient scheduling call spans language understanding, eligibility checks, available appointments, and a separate electronic health record (EHR) system. A natural conversation is useful only if the agent also knows when it can schedule, when it should hand off, and whether the external operation actually succeeded.

My contribution

In this project at 100ms, I implemented and hardened agent-side scheduling behavior: eligibility checks, routing between workflow paths, handoff conditions, booking-tool coordination, and visit explanations and notes. My work also addressed the conversation’s behavior while a booking operation was still running.

The EHR execution layer was part of the broader team platform. It used Temporal workflows and Playwright page objects to find the patient, select a slot, complete the booking, and check the returned result. My contribution described here focuses on the agent and its interaction with that layer.

Conceptual system boundary

  1. Collect and interpret the patient’s answers.
  2. Apply explicit scheduling and handoff rules.
  3. Prepare the tool request for the selected appointment.
  4. Run the booking through the platform’s Temporal and Playwright executor.
  5. Use the returned result to guide the next response and documentation.

Engineering decisions

Enforce prerequisites at the tool boundary.

Scheduling eligibility was represented in state and checked when a tool was invoked. My changes covered plan and pharmacy-related requirements and handoff conditions, keeping the conversation and the tool’s allowed behavior aligned.

Preserve why the agent chose a path.

I worked on routing based on information collected during the call and on carrying the trigger reason through tool handling. Visit explanations and generated notes made the decision understandable beyond the spoken response.

Handle the time spent inside a tool.

A browser-based booking can take longer than an ordinary conversational turn. I changed silence-response behavior so the agent would not interrupt an in-progress tool call with an unnecessary “Are you there?” prompt.

Treat booking as a confirmed external operation.

The platform executor returned success or failure after its booking steps. That boundary matters: selecting an appointment in conversation and completing the EHR write are separate events. The surrounding executor also managed browser capacity, credential allocation, and error handling.

Validation and result

My historical changes included prompt regressions and tests around eligibility, schema output, routing, and tool-argument handling. The broader executor repository contains its own workflow and browser-flow coverage.

This is an account of implemented agent behavior and integration work. It does not attribute the whole EHR automation stack to me or imply that a historical implementation has been revalidated against the live EHR today.

A scheduling agent needs to know the difference between discussing an action, requesting it, and confirming it happened.
