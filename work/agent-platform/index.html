A voice agent is part of a larger system

I’m a core contributor to the AI agent platform at 100ms. My work spans the conversation application and the services around it: shared schemas, case processing, backend integration, evaluation, and production operations.

The boundaries are important. A correct conversation can still produce an unusable outcome if a generated model, backend field, dashboard, or completion rule interprets the result differently.

Shared schemas and generated models

Protocol Buffers and Buf provide the schema foundation. Definitions include field types and enums, with annotations for UI rendering, validation, and AI extraction. The generation pipeline produces Go and TypeScript bindings, JSON Schema, and Pydantic models .

I work on field definitions and extraction guidance within these shared contracts. A schema change can affect what the agent extracts, how a form displays a field, and how an output is validated, so its consumers have to move together.

Python services and Go workflows

The conversation and case-processing applications use Python, FastAPI, asyncio, and Pydantic . Case-processing services prepare inputs, submit calls to the scheduler, generate summaries, and integrate with the case-management backend through gRPC .

The backend uses Go , HTTP/gRPC APIs, MongoDB , and Redis . Temporal coordinates workflows and activities, with task queues, retries, signals, and queries. Booking tools can invoke those workflows and consume an explicit result.

Stedi provides payer search and insurance eligibility integration. LLM-based summaries use OpenAI with Langfuse tracing and prompt management.

Interfaces for the people reviewing the work

The web dashboard uses React and TypeScript , with TanStack Query for server state, React Hook Form and Zod for forms and validation, and Radix UI primitives. Shared field definitions connect these interfaces to agent extraction and output data.

The goal is consistency: reviewers and applications should be looking at compatible representations of the information collected during a call.

Deployment and runtime configuration

Applications are packaged with Docker and deployed to GCP/GKE . Helm templates describe Kubernetes workloads; Argo CD syncs the deployment configuration from Git. Terraform and Terragrunt define infrastructure.

The deployment setup includes workload health and resource configuration, scheduled jobs, metrics discovery, and Vault integration for secrets. I have also worked on operational cleanup behavior, including preserving in-flight call directories and making job failures visible.

Configuration is not identical in every service. The voice application uses Unleash , while case-processing services also use the backend’s ConfigStore . Naming those boundaries matters when investigating which setting actually controlled a call.

Observability and access controls

The stack uses Prometheus instrumentation, Grafana , VictoriaMetrics/VictoriaLogs , OpenTelemetry , and New Relic . BigQuery supports audit analysis. These provide different views of the same system: operational metrics, logs, traces, and call-quality data.

The surrounding platform includes Auth0 authentication, Casbin role-based authorization, and Vault secrets management. My privacy-related work includes PHI-redacted transcript access for audit tooling.

How I approach changes across these layers

I trace a change from the field or conversation rule through its consumers, then check the relevant boundaries: generated models, extraction behavior, shared decision scenarios, backend outputs, and deployment configuration. The task is to make the pieces agree, and to keep enough evidence to explain a failure when they do not.
