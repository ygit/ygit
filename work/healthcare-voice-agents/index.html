Healthcare voice agents

Turning complex benefits-verification requirements into dependable conversations and structured outcomes.

Context Engineering at 100ms

Focus Conversation design · Python · LLMs

Scope Selected contributions; conceptual descriptions.

The problem

A useful healthcare voice agent needs to do more than hold a conversation. It needs to ask the right questions for the plan, handle incomplete or corrected answers, and turn what the representative actually confirmed into a usable result.

My contribution

At 100ms, I develop and harden healthcare conversation workflows, including medical and pharmacy benefits verification. My work connects prompt behavior, extracted fields, topic-completion rules, and downstream decision logic.

Conceptual workflow

  1. Choose questions from the workflow and known context.
  2. Capture the representative’s response.
  3. Extract structured information and preserve confirmation state.
  4. Evaluate the remaining questions and completion criteria.
  5. Produce an output that downstream systems can interpret.

Decisions that matter

Keep unknown information explicit. An unanswered question, a negative answer, and an affirmative answer are different states. Collapsing them can retire a question too early or send a call down the wrong path.

Let confirmed information guide the workflow. Supplied case data can differ from what a representative confirms. I have worked on gates that require that confirmation before applying plan-specific behavior.

Keep prompts and business rules aligned. If a workflow stops asking a question, the downstream engine must understand when that field is no longer required.

How I validate changes

My changes include prompt-render checks, extraction and workflow regressions, and scenario tests for shared decision logic. Cases cover plan-specific behavior, ambiguous answers, missing information, and resumed calls.

What this work enables

Explicit rules for when to ask, when to stop, and what counts as confirmed information—supported by regression coverage across the conversation and output layers.

The conversation and the resulting data need to tell the same story.

This overview uses no patient data or production transcripts.

The software behind the conversation

The application stack uses Python, FastAPI, and asyncio for services and asynchronous I/O. Jinja2 renders prompt templates; Pydantic defines typed data structures. Model calls use services including OpenAI and Gemini , with structured extraction feeding the conversation state.

Telephony and speech sit around this logic: Twilio connects calls, Deepgram recognizes speech, and ElevenLabs or Cartesia generates audio. My case-study focus here is conversation and data behavior within that larger system.

A concrete state problem

In a synthetic example, a coverage field can be absent, explicitly negative, or affirmative. Treating absence as false can move the agent past an unanswered question. The ask condition and the output rule must preserve the same distinction.

A second problem appears when an answer is available in the transcript before extraction has committed the field. Regression coverage needs to check the next conversational step, not only the final output.

From tools to backend operations

Booking tools in the stack use the Temporal Python client to start workflows and await their results. Other services communicate through gRPC and Protocol Buffers . This connects an agent’s tool call to a typed operation with an explicit result, rather than relying on conversational text as the system of record.

Rollout and investigation

Unleash controls feature rollout. Langfuse supports LLM tracing and prompt workflows; Cekura exercises conversation behavior. Services run in a broader Docker, GCP/GKE, and Kubernetes environment, with Prometheus, Grafana, and OpenTelemetry supporting operational investigation.
